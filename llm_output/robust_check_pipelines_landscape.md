# Checkable analysis with LLMs: who else is trying, and what to borrow

Claude-drafted, 23 October 2026, in response to [Dan's journal entry of 22 October](../human_journal/dan_journal.md). Sources checked on 23 October 2026. Section 1 was revised the same day to separate chat-based from agent-based evidence, and to add King and Worthington's October 2026 study of AI peer reviews.

The question: which other projects are building robust-check pipelines for work like this? That means quantitative work, not necessarily academic, with points where people can pick through and test it, and with ethical LLM use built into review on GitHub.

## The short version

- **Nobody I found has the whole package.** That would be a public quantitative project where every claim is split into small checks, each check records who or what ran it, and outside reviewers can test any piece on GitHub. But each part exists somewhere, usually in a different community: government analysis standards, open-source software review, reproducibility checking and formal maths.
- **The evidence backs the small-steps instinct, but much of it is from the chat era.** In a 2024 trial using ChatGPT, AI-led checking did much worse than human or AI-assisted checking. In the 2026 studies so far, coding agents reproduce published numbers much more reliably, but their conclusions can be steered and still pass review, and the same model does better or worse depending on the agent set-up. Nobody has yet compared chat, ad hoc agent use and structured agent set-ups head to head on research tasks. Everywhere, the limit is human checking time.
- **AI reviewing is now strong on reading and critique.** In a blinded test released in October 2026, AI reviews of 124 manuscripts beat high-quality, well-paid human pre-submission reviews on every measure the authors constructed. But the AI read only the manuscripts, not code or data, and the test measured the quality of the reviews, not whether papers improved.
- **The closest models to copy** are the Aqua Book's roles, the AI policies of GitHub-based software review (rOpenSci, pyOpenSci, JOSS), CODECHECK's independent reruns, Xu and Yang's structured agent workflow for reproducing papers, King and Worthington's proposal that authors answer an AI review in writing, and the "blueprint" dependency graphs used in large maths projects. The last is close to the dashboard idea.

## 1. What the evidence says

Much of the evidence people cite comes from chat-style use in 2024. Studies of coding agents working directly on files and code arrived in 2026, and they tell a different story. I found no study that compares chat, ad hoc agent use and a structured agent set-up head to head on the same research tasks. The nearest comparisons are for reviewing manuscripts, not analysing data (see "AI as reviewer" below).

### Chat-based use, 2024

- **AI-assisted checking held up; AI-led checking didn't.** The Institute for Replication randomly assigned 288 researchers to 103 teams, which tried to reproduce published quantitative social science as human-only, AI-assisted or AI-led teams. Human-only and AI-assisted teams reproduced results at similar rates. AI-led teams did far worse and proposed weaker robustness checks. Human-only teams found more major coding errors than either kind of AI team ([Brodeur et al., PNAS 2026](https://doi.org/10.1073/pnas.2524747123); [LSE summary](https://www.lse.ac.uk/european-institute/news/2025-26/comparing-human-only-ai-assisted-and-ai-led-teams-on-assessing-research-reproducibility-in-quantitative-social-science)).
- **But the AI was a chat window.** The seven games ran from February to November 2024 on ChatGPT (GPT-4 or GPT-4o), with file upload, a Python sandbox and web access. The authors call the AI-led arm "proto-agentic". People relayed files and prompts to ChatGPT but weren't allowed to read the paper, code or data themselves, and the replication code was in Stata or R while ChatGPT's sandbox ran Python. Participants reported "hallucinated paths, truncated context windows, and prolonged debugging loops". The authors call their result "only a lower bound" and suggest tools "with native support for R and Stata". The AI-assisted teams that kept pace with the humans "strategically outsourced micro tasks", such as boilerplate code and finding files, "while retaining conceptual control".

### Coding agents, 2026

- **Agents now reproduce published numbers far more often.** [SocSci-Repro-Bench](https://arxiv.org/abs/2606.11447) (Alizadeh and others, June 2026) tested Claude Code and Codex on 221 reproduction tasks across four social science disciplines. Both reproduced a large share, with Claude Code well ahead, at rates above those reported for earlier general-purpose LLM agents. Xu and Yang's structured Claude workflow (see section 2) fully reproduced 94.4% of the sampled political science papers whose materials were available. Neither is like-for-like with the I4R trial: they match published estimates rather than hunt for errors, and have no human comparison group.
- **Running the code still isn't checking the claim.** Agents can now reproduce results from code they're handed. But on [REPRO-Bench](https://arxiv.org/abs/2507.18901), which asks agents to judge whether a social science paper can be reproduced from its data and code, the best score is still about 35% ([Daniel Kang, December 2025](https://ddkang.substack.com/p/claude-45-opus-solves-core-bench)). Xu and Yang build the distinction into their workflow: "Running an author's code successfully does not by itself establish that the paper's reported results have been reproduced."
- **The numbers hold up better than the conclusions.** A [companion paper](https://arxiv.org/abs/2606.11456) to SocSci-Repro-Bench ran Claude Code and Codex 20 times each on the data from a well-known many-analysts study of immigration and social policy. Their estimates broadly matched the human consensus. But a confirmatory prompt moved Claude Code's verdicts from 10% to 90% support while its coefficients stayed "essentially unchanged". The authors conclude that "the locus of AI bias is not estimation but interpretation". The benchmark paper adds that subtle prompt framing can nudge agents towards confirmatory specification search, and that giving them the paper's PDF biased them on tasks that couldn't be reproduced.
- **A biased analysis can pass review.** In [The Agentic Garden of Forking Paths](https://arxiv.org/abs/2607.01507) (Miao, Pritchard and Zou, July 2026), Claude Code agents (Sonnet 4.6, with file, shell and Python tools) given different personas reached opposing conclusions from the same data. Codex (GPT-5.4) reviewed the reports, so that no model graded its own work. 86% passed that AI review, and 78% passed review by a majority of human experts. The authors suggest using agents to sample many defensible ways of running the analysis, then reporting how extreme the published result is among them (their "m-value").
- **The set-up matters, not just the model.** [Kohler and others](https://arxiv.org/abs/2604.21965) (ETH Zurich, April 2026) gave agents only a paper's methods description and its data, never the original code or results, for 48 papers that I4R had verified. They crossed four agent scaffolds (Claude Code, Codex CLI, mini-SWE-agent and OpenCode) with four models (GPT-5.4, GPT-5.3 Codex, Claude Opus 4.6 and GLM-5). With GPT-5.4 alone, the share of coefficients with the right sign ranged from 75% to 91% depending on the scaffold, against 68% for a rule that always guesses positive: "The scaffold-model interaction matters a lot." The best combination also used far more tokens. On REPRO-Bench, a purpose-built agent running the older GPT-4o still beat a generic agent running GPT-5.2 or Claude Opus 4.5 (Kang, above).

### AI as reviewer, 2026

- **AI reviews now beat strong human reviews of manuscripts.** [King and Worthington](https://gking.harvard.edu/peerless/) (Harvard, October 2026) compared AI and human reviews of 124 papers sent to rapidPeer, a Harvard pre-submission review service. Its reviewers are chosen by experts and paid well, and 88% of surveyed authors rated their reviews high or very high quality. 114 of the 134 review pairs were for quantitative-statistical papers. Claude Opus 4.8 wrote one review per paper in a single call, working from the manuscript PDF. A GPT-5.5 judge, blind to authorship and from a different model family, preferred the AI review in all 132 decided pairs. Three former journal editors, who didn't know AI was involved, preferred it in 26 of 30 judgements. The AI made incorrect claims about the manuscript about a third as often as the humans (5.5% of claims against 15.9%), and cited no fabricated sources. In the authors' words, AI reviews are "better, by every measure we could construct".
- **Read the scope carefully.** The AI saw only the manuscript, not code, data or supplementary files, so this is evidence about reading and critique, not about checking computations. The study measured the quality of the reviews: the AI reviews were never sent to authors, and the authors "did not measure the degree to which subsequent revisions improved the paper". The editors judged the reviews without reading the manuscripts. The authors say the results speak to helping authors improve papers, not to how editors should decide what to publish.
- **For this task, the set-up mattered less.** A version with no tools, given the human reviewers' guidelines, did almost as well as the web-enabled version with a purpose-built prompt. The exception was sources, where it won 62% of pairs instead of 100%. The [AAAI-26 pilot](https://arxiv.org/abs/2604.13940) gave each of 22,977 conference papers one clearly labelled AI review from a multi-stage pipeline with tools. On a new benchmark, that pipeline did much better than a simple LLM review at detecting scientific weaknesses, and authors and committee members preferred its reviews to human ones on key dimensions such as technical accuracy.
- **Their policy options, and the dangers.** King and Worthington sketch five options for journals. They range from authors running AI reviews themselves before submitting, through journals publishing an official review prompt, to an editor deciding from a dossier: the paper, an AI review from the published prompt, the author's reply to it, and a second AI review from a prompt the editor keeps private. The author's reply matters "so that AI model creators do not get to determine the content of scholarly papers". Banning AI from reviewing may already be futile: in a [randomised experiment at ICML 2026](https://arxiv.org/abs/2609.19420), 22.5% of reviewers assigned to a no-AI policy said they used an LLM anyway, and the policy made almost no difference to decisions or scores. The dangers they name are science drifting towards "the conventional, orthodox, and majoritarian", and authors optimising for the published prompt's "explicit and implicit reward model". Whether a paper meets a journal's standards, they argue, "can only be decided by a human journal editor".

### Does the structure in the folder help?

- **Only when it carries knowledge the agent can't find for itself.** [Evaluating AGENTS.md](https://arxiv.org/abs/2602.11988) (ETH Zurich, February 2026) found that repository instruction files, whether written by developers or by LLMs, generally didn't raise coding agents' success rates and added more than 20% to cost. They were useful for "specifying non-standard coding practices", but repository overviews didn't help. [SkillsBench](https://arxiv.org/abs/2602.12670) (February 2026, 87 tasks in eight domains) found that curated skills raised average pass rates from 34% to 51%, and that focused skills with at most three modules beat bigger bundles. Neither tests research analysis. Read together, they suggest structure helps when it holds procedures or knowledge the agent can't work out for itself, not when it restates what's already in the repo.

### What usage data can and can't show

- **Anthropic splits its data by product, not by practice.** Several of its reports separate Claude Code from chat. In the [2025 software development report](https://anthropic.com/research/impact-software-development), 79% of Claude Code conversations were automation, against 49% on Claude.ai. [Measuring AI agent autonomy in practice](https://www.anthropic.com/research/measuring-agent-autonomy) (February 2026) tracks how long agents run unsupervised. The June 2026 [Cadences report](https://www.anthropic.com/research/economic-index-june-2026-report) says "Chat transcripts no longer fully capture how people are using AI", and that "the product used is likely more important than the underlying model". [Agentic coding and persistent returns to expertise](https://www.anthropic.com/research/claude-code-expertise) (June 2026, about 400,000 Claude Code sessions) found verified success, such as commits, passing tests or the user confirming it worked, in 15% of sessions rated novice, against 28–33% for the rest. It concludes that "Coding agents are not substituting for domain expertise".
- **But the gaps are the ones that matter here.** The headline [productivity estimate](https://www.anthropic.com/research/estimating-productivity-gains) (about 80% of task time saved) uses Claude.ai chats only, and can't see the time people spend checking Claude's work. None of these reports measures how the work is set up (instruction files, skills, tests, notes) or real-world outcomes. User expertise is the closest proxy.
- **Clean experiments are getting harder to run.** In early 2025, METR's trial found that experienced open-source developers took 19% longer with AI tools, mainly Cursor. Its [February 2026 update](https://metr.org/blog/2026-02-24-uplift-update/), as agents like Claude Code and Codex spread, pointed to speed-ups instead, but with confidence intervals that include no effect. Developers increasingly refused to work without AI or held tasks back, and METR now calls its data "an unreliable signal".

### Checking is the bottleneck

- **Human checking time is the limit.** [Catalini, Hui and Wu (2026)](https://arxiv.org/abs/2602.20946) argue that "the binding constraint on growth is no longer intelligence but human verification bandwidth". Andrej Karpathy's talk [Software Is Changing (Again)](https://www.ycombinator.com/library/MW-andrej-karpathy-software-is-changing-again) gives the practical version: keep the AI on a short leash, work in small increments, and make the loop of AI generating and a human checking as fast as possible.
- **The overload has arrived.** Pangram [estimated](https://www.pangram.com/blog/pangram-predicts-21-of-iclr-reviews-are-ai-generated) that 21% of reviews for the ICLR 2026 machine learning conference were fully AI-generated. arXiv's computer science section [stopped accepting](https://blog.arxiv.org/2025/10/31/attention-authors-updated-practice-for-review-articles-and-position-papers-in-arxiv-cs-category/) review and position papers that hadn't been peer reviewed, citing an "unmanageable influx". curl [ended its bug bounty](https://daniel.haxx.se/blog/2026/01/26/the-end-of-the-curl-bug-bounty/) after the share of reports that were real vulnerabilities fell from over 15% to under 5%. GitHub now lets maintainers [limit who can open pull requests](https://github.blog/changelog/2026-02-13-new-repository-settings-for-configuring-pull-request-access/).

## 2. Who's building what

### UK government analysis standards

- **[The Aqua Book](https://www.gov.uk/guidance/the-aqua-book)**, the government's guidance on producing quality analysis (new edition, July 2025), defines four roles: commissioner, analyst, assurer and approver. The assurer must be independent of the analyst, assurance should be proportionate to the risk, and the new edition covers AI and other "black box" methods.
- **[The Duck Book](https://best-practice-and-impact.github.io/qa-of-code-guidance/)** (*Quality assurance of code for analysis and research*, from ONS for the Government Analysis Function) has code QA checklists and chapters on peer review and testing. Its [generative AI page](https://best-practice-and-impact.github.io/qa-of-code-guidance/generative_ai.html) says "The only person responsible for the code you generated with an LLM is you", and that LLM code should never go to peer review before you've reviewed it yourself.
- **[Reproducible Analytical Pipelines](https://analysisfunction.civilservice.gov.uk/support/reproducible-analytical-pipelines/)** (RAP) set minimum standards: few manual steps, version control, peer review and open code. Testing, input data validation and automatic checks on every change come next.

### Peer review on GitHub, now with AI policies

- **[rOpenSci](https://ropensci.org/blog/2026/02/26/ropensci-ai-policy/)** reviews R packages in public GitHub issues. Its draft AI policy (February 2026, still being tested) asks authors to describe their AI use, including any agent instructions file, and lets reviewers use AI as long as the judgements are their own. It makes two points worth keeping. Asking authors to flag the AI-written parts could shrink review to just those parts. And "We do not want software review to become a service in which our human volunteers validate largely AI-generated software."
- **rOpenSci's [srr](https://docs.ropensci.org/srr/) package** links each statistical standard to the lines of code that meet it, and lists the standards still to do. It's the nearest existing thing to a map from claims to code.
- **[pyOpenSci](https://www.pyopensci.org/blog/generative-ai-peer-review-policy.html)** (November 2025) asks for LLM use to be disclosed in the README and in the modules affected. LLM code must be "reviewed, edited, and tested by humans" before submission, so reviewers aren't left to vet it.
- **[JOSS](https://joss.readthedocs.io/en/latest/policies.html)** requires an AI usage section in every submission: the tools and versions, what they did, and a statement that humans reviewed and validated the output and made the main design decisions. Reviewers' judgements must be entirely their own.
- **[GAIDeT](https://www.leidenmadtrics.nl/articles/gaidet-a-practical-taxonomy-for-declaring-ai-use-in-research-and-publishing)** is a scheme for declaring AI use stage by stage, from design and data analysis to writing, with a [declaration generator](https://panbibliotekar.github.io/gaidet-declaration/index.html). UKRIO's [Embracing AI with integrity](https://ukrio.org/ukrio-resources/embracing-ai-with-integrity/) (June 2025) covers the research-integrity side for UK researchers.

### Independent checks

- **[CODECHECK](https://codecheck.org.uk/)**: an independent codechecker reruns a paper's code and issues a certificate with a DOI. There are 132 so far. One of its principles is that checkers "record but don't investigate or fix", which is a good rule for a checking agent too.
- **[RegCheck](https://arxiv.org/abs/2601.13330)** uses an LLM to compare a study's preregistration (the plan written before seeing results) with the published paper. It shows the relevant text for each item and leaves the call to a person, "facilitating (rather than replacing) human discrepancy judgements".

### Agent pipelines with human gates

- **[Xu and Yang's reproducibility workflow](https://yiqingxu.org/papers/2026_ai/AI_reproducibility.pdf)** (Stanford and Hong Kong Baptist University, February 2026) is the closest published example of a structured agent set-up for quantitative work. Claude orchestrates. `SKILL.md` files set out each stage's inputs and outputs, and record failure patterns already solved. Deterministic R, Stata or Python code does all the numbers, and the orchestrator is "excluded from numerical estimation and inference". There are gates between running the code, checking its output against the paper, and further diagnostics. Every intermediate result is written to disk ("Agents share no hidden state"), people review the failures, and recurring fixes become versioned rules. The authors ran it on 384 papers and 3,382 models from three top political science journals.
- **[HLER](https://arxiv.org/abs/2603.07444)** (March 2026) is a multi-agent pipeline for empirical economics, with data-auditing agents and human decision gates. Limiting research questions to what the dataset can support raised the share that were feasible from 41% to 87%.
- **Posit's [Databot](https://posit.co/blog/introducing-databot/)** (now part of Posit Assistant) works "in manageably-sized chunks before returning control back to you" and shows its code, because models still make mistakes in open-ended data exploration.

### Recording who did what in git

- **The Linux kernel's [AI coding assistants policy](https://docs.kernel.org/process/coding-assistants.html)** asks for an `Assisted-by:` tag naming the tool. An AI must never add the `Signed-off-by:` line. Only a human can, and doing so takes responsibility for the change.
- **[Fedora's policy](https://docs.fedoraproject.org/en-US/council/policy/ai-contribution-policy/)** (October 2025) uses the same `Assisted-by:` trailer, and says AI must not be "the sole or final arbiter" when contributions are reviewed.
- **[git-ai](https://github.com/git-ai-project/git-ai)** records which lines an agent wrote, with the model and prompts, in git notes, and adds an AI-aware `git ai blame`. Thoughtworks [rates it](https://www.thoughtworks.com/radar/tools/git-ai) as worth assessing. It's an alternative, or a complement, to the split commits in [human_llm_commit_tracking.md](human_llm_commit_tracking.md).

### Small checked steps, and dashboards that show them

- **Lean blueprints** ([leanblueprint](https://github.com/PatrickMassot/leanblueprint)): large maths formalisation projects lay out the argument as a dependency graph, a diagram of which small statements rest on which. Each node is coloured by status, from "not ready" through "stated" and "proved" to "fully proved", meaning proved along with everything it rests on.
- **The [Equational Theories Project](https://github.com/teorth/equational_theories)** (Terence Tao and others; [paper](https://arxiv.org/abs/2512.07087)) settled 22 million small implications. People, automated provers and AI tools each took pieces, and every result was checked in Lean before it counted. Progress is on a public [dashboard](https://teorth.github.io/equational_theories/dashboard/). Anything not yet machine-checked is labelled "conjectured", whether a person or a computer produced it.
- **[targets](https://docs.ropensci.org/targets/)**, the R pipeline tool, draws the pipeline as a dependency graph (`tar_visnetwork()`), colours up-to-date and outdated steps differently, and reruns only what has changed.
- **Jon Minton's [knowledge tree](https://ktandb.co.uk/knowledge-tree)** (Knowledge Tree and Butterfly) gives each output a manifest of what it was "grown from", so whether it's out of date is "decidable, at a glance, by a person or a do-bot".
- **[Octopus](https://www.octopus.ac/)**, funded by UKRI, publishes research in eight linked parts (problem, hypothesis, method, results, analysis, interpretation, application and peer review), each of which can be reviewed on its own. It's the publishing-side version of chunks.
- **In AI research the same idea is called process supervision.** Training a model to judge each step of a maths solution gave a better checker than training it on final answers alone ([Lightman et al., 2023](https://arxiv.org/abs/2305.20050)).

## 3. What this suggests for RegEconWorks

1. **Keep "who wrote it" separate from "has it been checked".** A label saying Claude wrote something doesn't catch its errors. Track the check status of each claim, whoever wrote it, as the Equational Theories Project does.
2. **Give each step Aqua Book roles.** You commission and approve, and approval stays human, like the kernel's sign-off. Claude can be the analyst where the output can be checked: pipelines, reproducing published totals, standard-error code tested against a simulation. The assurer must be independent of whoever built the step: a fresh, read-only agent session that never saw the build, then a person. Judgement stays with you, such as what an LQ is meant to show, or how big an error would change your conclusion. Where possible, use a different model or harness for the automated check, as the forking-paths study did so that no model graded its own work.
3. **Write each claim down before running it.** One line each: the claim, what you expect, and what would show it's wrong. That works as a small preregistration, and the write-up can later be checked against it. It matters more with agents, because their numbers now hold up better than their conclusions: a confirmatory prompt flipped Claude Code's verdicts without changing its estimates. A decision rule fixed in advance is the defence.
4. **Make checks enforced, not requested.** Let the agent coordinate and let scripts do all the numbers, as Xu and Yang do. Checks that must always run belong in a script, a Claude Code hook or a GitHub Action, not in an instruction to the model. [ABS_direct_dataprep.R](../code/ABS_direct_dataprep.R) already has good ones: the regions sum to the UK, divisions plus remainders match the published totals, and 2012 to 2022 match the older extract. But some stop the script, some only warn and some only print a number. For a dashboard, each needs to record a pass or a fail.
5. **Show the spread where choices matter.** Where defensible choices differ, such as handling suppressed cells or the assumptions behind LQ standard errors, record the alternatives and how far they move the results, in the spirit of the m-value. [ABS_direct_suppression_test.R](../code/ABS_direct_suppression_test.R) already compares two ways of handling suppressed cells.
6. **Declare AI use per chunk.** Give each chunk a short AI-use statement in the JOSS or GAIDeT style, and use `Assisted-by:` trailers or split commits. If the project gets a `CLAUDE.md`, commit it, so readers can see what the agent was told. rOpenSci asks for the same.
7. **Keep instructions short, and put procedures in skills or scripts.** Instruction files mostly add cost unless they say something the agent can't work out, while focused, curated skills help. For this repo, that means a short `CLAUDE.md` holding only the non-obvious rules, with the check procedures as skills or scripts.
8. **Review one claim at a time on GitHub.** An issue for each claim or check lets an outside reviewer pick one small thing to test, rather than a whole chunk. GitHub's limits on pull requests and issues are there if noise arrives.
9. **Publish an AI review and your reply with each chunk.** This borrows King and Worthington's journal proposal. Keep the review prompt in the repo, and commit the AI review of each chunk with your reply: what you changed, and where you disagree and why. Human reviewers can then spend their time on the disagreements, and on what AI can't settle, such as whether the question matters for policy. Use a different model for the review from the one that helped write the chunk, and keep a list of the AI suggestions you rejected. Their evidence covers reading, not computation, so this adds to the checks above rather than replacing them.
10. **Record how each step was produced.** Tag each check result with how the step was made: a structured agent workflow, an ad hoc agent session, or by hand. The numbers will be small, but nobody seems to be making this comparison in the open.

### A dashboard sketch

This is small enough to build inside this repo.

- **A `claims.yml` file next to `chunks.yml`.** For each claim: the one-line claim, what it depends on (other claims and data steps), the script and output that produce it, and how it was produced (structured agent workflow, ad hoc agent session or by hand). Then each check on it: its kind (accounting identity, matches a published figure, simulation, human read-through, fresh-agent review or outside reviewer), the result, the date and commit, and who or what ran it.
- **A GitHub Action** that reruns the machine checks on every push and saves the results as JSON.
- **A Quarto page that draws the claims as a dependency graph, blueprint-style.** Grey means not yet checked, amber means machine-checked only, green means checked by a person, and red means failing or disputed. A "stale" flag shows when an input has changed since the last check. Each node links to its code, its output, its GitHub issue and the LLM conversation behind it.
- **Start with the ABS chunk and 10 to 20 claims.** If `targets` ran the pipeline, the graph and the staleness flags would come for free.
- **One test before building it:** does it make checking faster? If not, a plain table in the chunk will do.
