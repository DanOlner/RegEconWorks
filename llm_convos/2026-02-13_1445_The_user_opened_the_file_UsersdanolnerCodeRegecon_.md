Here's what I found on both questions:

**Custom contribution types:** The All Contributors spec *documents* a way to define custom types in the `.all-contributorsrc` config file, with a structure like:

```json
"types": {
  "custom": {
    "symbol": "🔭",
    "description": "A custom contribution type.",
    "link": "..."
  }
}
```

However, as discussed in [this GitHub issue](https://github.com/all-contributors/all-contributors/issues/528), **the custom contribution feature is incomplete** -- the bot doesn't actually recognise custom types via commands. A maintainer confirmed it remains unimplemented. So if you want bespoke categories, you'd need to either:

1. **Manually edit** the `.all-contributorsrc` JSON file and the generated contributor table in your README yourself, bypassing the bot entirely
2. **Fork the specification** -- it's [CC-BY licensed](https://allcontributors.org/docs/en/specification) -- and define your own contribution types for your project. Since the rendered output is just a markdown table, you control the format completely.

In practice, option 1 is the realistic one. The `.all-contributorsrc` is just a JSON file in your repo; the rendered table in the README is just markdown. You can write both by hand.

**Contributors without GitHub accounts:** The bot and CLI are designed around GitHub/GitLab usernames. But the [specification itself](https://allcontributors.org/docs/en/specification) says the contributor table should include a **name**, a **profile link** (described as "chosen at project discretion"), and **contribution categories**. The profile link doesn't have to be a GitHub profile -- it could be anything, or nothing.

So yes, you can absolutely add someone without a GitHub account by **editing the `.all-contributorsrc` file directly**. Each contributor entry in that JSON file has fields like `name`, `avatar_url`, `profile`, and `contributions`. You could set:

```json
{
  "name": "Jane Smith (Scottish Government)",
  "avatar_url": "",
  "profile": "https://their-org-website.gov.uk",
  "contributions": ["ideas", "data", "review"]
}
```

...and then manually update the markdown table in your README to match. The bot won't manage these entries for you, but they'll render the same way.

**Bottom line:** The All Contributors tooling is GitHub-centric, but the *specification* and the *output format* are just JSON + markdown. For a research project where contributors include civil servants and public sector people without GitHub accounts, you'd be maintaining the contributor list manually anyway -- which is fine, and arguably more appropriate than asking non-technical collaborators to create GitHub accounts just to be credited.

**Pros:** Keeps everything in one system; renders automatically from the config.
**Cons:** You'd be extending the JSON schema beyond what the bot understands, so bot-triggered updates could overwrite your customisations. Fragile.

### Option B: Multiple contribution categories as a proxy for level

Instead of a "level" field, use contribution *types* to imply depth. For instance:

- Someone who gave a brief comment gets `review` only
- Someone who did substantial work gets `ideas`, `review`, `doc`, `data` -- multiple emojis

**Pros:** Works out of the box with the bot; no custom config needed; visually intuitive.

You keep the `.all-contributorsrc` as the canonical data source (for anyone who wants machine-readable contributor info) but render a richer table yourself.

**Pros:** Full control; can express anything; clear to readers.
**Cons:** Two things to keep in sync (JSON + manual table); loses bot automation entirely.

### Option D: Hybrid -- CRediT-style levels in the JSON, render manually

Good question. The bot **appends to** the existing `contributors` array -- it doesn't rewrite the whole file. When you use `@all-contributors please add @someone for code`, it:

1. Reads the current `.all-contributorsrc`
2. Adds a new entry to the `contributors` array (or adds new contribution types to an existing entry)
3. Writes the file back

So manually-added entries (like non-GitHub contributors or custom fields like `level`) should survive bot updates. The bot only touches entries it's asked to modify.

**However**, there are two caveats:

- The bot **regenerates the markdown table** in your README between the `<!-- ALL-CONTRIBUTORS-LIST:START -->` and `<!-- ALL-CONTRIBUTORS-LIST:END -->` comments every time it runs. If you've manually edited that table (e.g. added a "Level" column), the bot will overwrite it with its standard format. So manual table customisations in the README are fragile.
- If a future bot update changes how it serialises the JSON (e.g. reorders keys, reformats), it could alter the file structure, though the data should be preserved.

**Practical upshot:** The `.all-contributorsrc` JSON is safe for manual additions. The rendered markdown table in the README is not -- the bot owns that. If you want a custom table format, either maintain it outside the bot's comment markers, or stop using the bot for table generation and do it all manually.

So you'd need to encode the level in a field the template can see (e.g. append it to the name: `"Dan Olner [substantial]"`) which is hacky.

**Not recommended.**
